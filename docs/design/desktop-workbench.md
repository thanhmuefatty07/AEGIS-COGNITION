# Desktop conversation workbench

Design handoff, 2026-09-29. The implemented workspace centers on a conversation and an optional evidence inspector. A project supplies context; it is optional for starting a chat. This document records the current React/CSS contract, rendered observations, and remaining verification limits.

Opening a project changes the active conversation store and file context. With no project, label the scope **Local chats** and offer **Choose a project**; with a project, show its name and label the list **Project chats**. Scope labels describe the active store, not a global aggregation. The profile store is not presented as an added project. New chat clears the conversation selection while retaining scope, draft, and attachments. A record is created on the first send and titled from that message. Unstarted records are filtered from the list without deleting their data. A scope switch refreshes the list and avoids displaying the previous scope's conversation as current.

## Confirmed file-memory relations — 2026-10-11

The inspector now has separate **Saved file-memory relations** and **Memory search candidates** sections. A lexical path match stays a candidate. Searching, selecting, and rendering do not write a relation; the user must click the candidate's clearly named save-link action. The request carries the selected project, source revision/path/hash, and memory ID/scope/revision/hash for backend revalidation. Relation API project keys use `project:<workspace-project-id>`; the graph keeps the workspace's raw project ID for candidate provenance and normalizes it at the relation boundary. The backend creates the relation ID. Linking records provenance only and never promotes a memory: retrieval-eligible CANDIDATE or ACTIVE records with UNREVIEWED or ACCEPTED validation can be linked, and their lifecycle/validation stays unchanged. The lexical match remains labeled as a candidate after saving, and no owner ID is rendered.

Saved relations display the memory ID and scope, target path, saved source and memory revisions/hashes, lifecycle/validation, and one of four statuses: **Current**, **Stale source**, **Stale memory**, or **Memory not active**. Current means both source and memory evidence match and the record remains retrieval-eligible; CANDIDATE/UNREVIEWED records can therefore be Current. “Memory not active” means its lifecycle or validation no longer qualifies for recall. Source freshness compares project/path/file hash; a workspace revision change alone does not make a link stale or offer a duplicate link for unchanged file and memory hashes. Unlink sends only the displayed relation ID plus its project/path/scope binding and removes that relation alone. Late relation-list and write responses are ignored when the selected project, path, or file hash has changed.

### Bounded saved-relation history — 2026-10-12

The inspector loads at most 24 saved relations initially and requests later pages only after **Load more saved relations** is selected; each request is capped at 100 rows. SQLite applies the owner, scope, project, and path filters before `LIMIT`. Continuation uses the saved timestamp plus the numeric order of the decimal relation ID, so equal timestamps and IDs with different digit counts remain stable across pages. No offset scan is used. The Desktop protocol carries a bounded cursor string bound to owner, scope, project, and path, and protected by HMAC-SHA256 using a key held in service memory. Its base64 payload is not confidential. A cursor is continuation state, not authorization: memory access is rechecked on every page. Recreating the service invalidates outstanding cursors; the inspector can restart history from page one. The UI accepts a page only while the same project, path, and source hash remain current. If the source hash changes during a later-page request, the UI invalidates that request, clears its loading state, and hides the stale relation list until the file is selected again. Save-link and remove-link actions are disabled while a page is loading, so mutations cannot cancel an in-flight page and discard its continuation cursor. The pre-existing unpaged Python API remains available for compatibility. This UI history change does not alter the separate provider-context query, which already applies its own SQL-side limit; no reduction in model-token use is claimed.
